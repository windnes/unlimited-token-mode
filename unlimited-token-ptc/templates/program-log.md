# 程序账本（program log）—— 无限tokenPTC版

> 本文件是**契约 2（状态外置）**与**契约 7（可证伪收工）**在 PTC 下的载体。
> **每个 `run_code` 程序一条记录，不多不少。** 没有记录的程序等于没有执行过 ——
> 因为 `per-call` 模式下每次调用是全新 VM，变量不跨调用存活；`persistent-in-memory` 模式下变量活着，
> 但不可见、无 `_rev`、无并发保护。两种模式都不能当账本，账本只能落盘到本文件。
>
> 校验：`python scripts/ptc_lint.py <本文件> --kind program`
> 严格档：追加 `--strict`（额外校验 `description` 词数、`意图` 是否多意图、`证据` 块是否疑似吞异常）。
>
> 落盘位置：`state/programs.md`。它和 `state/run.json`（权威状态）、`state/events.jsonl`（事件日志）、
> `state/aggregate.json`（聚合）一起构成唯一状态来源。**程序变量不是状态来源。**

---

## 块格式（与 spec §6 逐字一致）

> 以下是格式说明，**不要复制外层围栏**。真实记录写在本文件里时不带外层围栏（见下面两个示例）。
> 字段名逐字使用，不得改写成同义词；九个字段缺一即校验失败。
>
> 围栏规则（v2.1 已修正）：
> - **行首无缩进**的围栏 = 格式示例或引用代码，里面的程序块不会被当成真实记录。
> - **缩进 ≥2 空格**的围栏 = `- 证据:` 这类字段的值，正文会被保留并参与校验。
>   v2 把两种围栏一视同仁地清空，于是本模板照原样跑 `--kind program` 直接报
>   `PRG-FIELD-EMPTY`——模板自己过不了自己的校验。
>
> **证据档（v2.2）**：装了 `utc-ledger` 且框架发出 `tool/ptc-dispatch` 事件时，
> 内层调用会以 `scope: "inner"` 落账，`command` 是真实命令、`exit` 来自真实执行。
> 此时 `--ledger` 校验是 `ledger` 档，**证据里的 `exit=` 必须与该内层记录一致**。
> 若账本里只有外层 `run_code` 记录，证据档降为 `source-literal` 并给
> `LEDGER-EXECUTION-UNPROVEN` 警告——这一档不证明命令被执行过。

````text
## 程序 <n> @ <ISO 时间>
- 程序 id: P<n>
- description: <主动语态，5–10 词；中文按字数 8–40 字>
- 意图: <一句话，一个意图>
- 不可逆动作: 无 | <具名实体> <动作>
- 状态读写: <文件 + _rev 变化，如 state/run.json _rev 7 → 8；无状态则写「无」>
- 证据:
  ```text
  $ <命令或 tools.<name>(...) 调用>
  exit=<整数>
  <原始输出，可截断但不可改写>
  ```
- 判决: pass | fail | partial
- 可失败性: <如果实现错了，这条证据会怎么变红>
````

字段说明：

| 字段 | 填什么 | 常见填错 |
| --- | --- | --- |
| `## 程序 <n> @ <ISO 时间>` | `n` 是本文件内递增序号；时间是该程序**开始时**的时间，不是补记时间 | 用本地时间但不带时区偏移 |
| `程序 id` | `P<n>`，与 `## 程序 <n>` 的 `n` 一致，并与决策日志、运行报告引用一致 | 写成 `program-1`、`#1` |
| `description` | 原样粘贴该 `run_code` 的 `description` 参数：主动语态 5–10 词；中文按字数 8–40 字 | 事后重写得更漂亮，导致与实际调用不一致 |
| `意图` | 一句话，一个意图。**不得**用「和」「以及」「顺便」「同时」把两件事缝起来 | 写"改配置并重跑测试" |
| `不可逆动作` | 没有就写「无」；有就写 `<具名实体> <动作>` | 写"删了点东西"（实体不具名） |
| `状态读写` | 写文件与 `_rev` 变化；纯读也写（`_rev 7 → 7`） | 写"更新了状态"（没说哪个文件、rev 怎么变） |
| `证据` | 一个 `text` 代码块，内含 `$ ` 调用行、`exit=` 行、原始输出 | 只贴一句"3 个文件已改，都正常" |
| `判决` | `pass` / `fail` / `partial` 三选一 | 写 `ok`、`成功`、`PASS（带括号备注）` |
| `可失败性` | 如果实现错了，这条证据会怎么变红 | 写「无」「N/A」「-」「不会失败」 |

## 示例 1：`判决: pass`（可被 lint 校验，不在围栏里）

## 程序 1 @ 2026-10-25T13:42:07+08:00
- 程序 id: P1
- description: 读取任务状态并核对修订号
- 意图: 核对 state/run.json 的 _rev 是否等于事件日志末行记录的 rev
- 不可逆动作: 无
- 状态读写: state/run.json 只读（_rev 7 → 7）
- 证据:
  ```text
  $ await tools.read({ path: "state/run.json" })
  exit=0
  {"_rev":7,"step":"verify","done":["C1"],"programs":1}
  ```
- 判决: pass
- 可失败性: 若上一段程序未落盘，返回的 _rev 会是 6；若发生并发写覆盖，会返回 8 或事件日志末行与 _rev 不匹配。两种情况下返回的 JSON 会直接显示不一致的数字，本块判决必须改为 fail 并重读，而不是继续往下写。

## 示例 2：`判决: fail`（可被 lint 校验，不在围栏里）

## 程序 2 @ 2026-10-25T13:47:31+08:00
- 程序 id: P2
- description: 运行程序账本校验程序
- 意图: 验证程序账本能通过 program 档校验
- 不可逆动作: 无
- 状态读写: 无
- 证据:
  ```text
  $ python scripts/ptc_lint.py state/programs.md --kind program
  exit=1
  FAIL program @L12: 证据块缺 exit= 行
  FAIL program @L12: 判决 pass 但证据既无 exit=0 也无数字
  PASS program @L31: 九字段齐全
  ```
- 判决: fail
- 可失败性: 若 L12 那条记录补上 `exit=0` 与原始输出，两条 FAIL 会同时消失、exit 变成 0。当前输出点名了具体行号与缺失项，任何人重跑都能得到同一结论，因此这条失败可被推翻。

## 判决取值

| 判决 | 什么时候用 | 允许收工吗 |
| --- | --- | --- |
| `pass` | 证据完整、`exit=0`、且 `可失败性` 写清了"实现错了会怎么变红" | 允许，但同一判据的全部证据块都要是 pass |
| `fail` | 证据显示期望与实际不符；或程序抛了 `ToolCallError` 且未吞掉 | 不允许；必须修完再写新的程序块，旧块保留不删 |
| `partial` | 部分证据通过，但有未验证项：被 `timeoutMs` 杀掉、被 `maxOutputBytes` 截断、只验了 A 没验 B | 不允许直接收工；必须同步写进运行报告 §3 未验证项 |

`partial` 的存在意义：P6（截断即完成）最常见的表现就是把 `partial` 写成 `pass`。
被 `timeoutMs` 杀掉的程序没有正常退出，它的输出不完整，`exit=` 也不是 0 —— 这种情况只能是 `partial` 或 `fail`。

## 常见错误

| 错误 | 对应缺陷 | 症状 | 修法 |
| --- | --- | --- | --- |
| 吞异常导致假 pass | P1 | `catch {}` 或 `catch (e) { return { ok: true } }`，`ToolCallError` 消失，块里只剩 `exit=0` | 去掉 `catch`，或 `catch` 里 `throw` / `return` 原始错误对象；证据块里保留报错原文 |
| 自证判决 | P2 | 只 `return { allPass: true }` 或 `return { passed: 3 }`，没有原始输出 | `return` 原始值：`exit=`、原始输出片段、diff；程序不替读者下结论 |
| 摘要代替证据 | P3 | 证据块写"3 个文件已改，都正常" | 贴 diff 或文件内容片段，截断处标明截断 |
| 变量当状态 | P4 | 进度、计数、已改清单只存在程序变量里，账本与 `state/run.json` 里查不到 | 每程序结束前写 `state/events.jsonl` 并更新 `state/run.json` 的 `_rev`；本文件同步加一条 |
| 捆绑不可逆 | P5 | `不可逆动作` 写了两个，或动作没写进 `description` | 拆程序：一个程序 ≤ 1 个不可逆动作；`description` 必须点名它；同时在决策日志留 `## 决策` 块 |
| 截断当完成 | P6 | 程序被 `timeoutMs` 杀掉或被 `maxOutputBytes` 截断，判决仍写 pass | 判决改 `partial`，证据里标明截断点，运行报告 §3 登记未验证项 |
| 并发读改写 | P7 | `Promise.all` 里对同一状态文件读-改-写，`_rev` 失效或丢失更新 | 读可并发，写必须串行、按提交顺序；同一文件的读-改-写放进同一个串行段 |
| 无 exit 行 | — | 证据块只有输出，没有 `exit=` 行，或没有以 `$ ` 开头的调用行 | 补上调用行与退出码；`tools.<name>(...)` 调用也写 `exit=0`（成功）或 `exit=1`（抛错） |

## 与决策日志的联动

- 本文件里 `不可逆动作` 不是「无」的程序，必须在同一交付里存在至少一个 `## 决策` 块
  （`--kind decision` 格式），并通过 `程序 id` 关联。
- 决策块的三栏 `程序 id` / `description` / `程序内不可逆动作数` 必须与本文件自洽：
  本块 `description` 原样出现在决策块里；本块涉及的不可逆动作数就是决策块里那个整数。
- 若推演后把不可逆动作拆成了两个程序，两个新程序各写一条本文件记录，决策日志也各补一块。
