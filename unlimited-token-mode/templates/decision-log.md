# 决策日志（decision log）

> 契约 3（后果推演门）的载体。**每一个不可逆动作前写一个块，不是事后补。**
>
> 校验（推荐，能查出编造与改写）：
> ```bash
> python scripts/unlimited_lint.py decisions.md --kind decision --ledger "$DSH_HOME/.utc/ledger.jsonl"
> ```
> 没有账本时只能做形态检查：
> ```bash
> python scripts/unlimited_lint.py decisions.md --kind decision
> ```
>
> **核心禁令（本版已实现，不再是口号）**：指出风险却不改变动作，等于没指出。
> 若"二阶"栏写了具名实体 + 可量化成本，而"决定"栏仍是 `act` 且没有缓解措施，
> 校验器直接判失败（`DEC-CORE-PROHIBITION`）。v1 只把这句话写在文档里，代码从未实现。

---

## 固定块格式

```
## 决策 <n> @ <time>
- 动作: <我即将做什么>
- 受影响实体: <具名实体>
- 触发规则: <规则 id + 它推动哪个计数>
- 该规则读取的量: <规则消费的那个变量>
- 我核对过的量: <命令> → <真实输出>
- 二阶: <规则触发 -> 哪个实体 -> 什么成本（数字+单位）>
- 三阶: <该实体的反应 -> 导致什么>
- 不可逆性: <可逆？撤销成本？>
- 反事实: <什么都不做 / 最小替代 -> 差异>
- 决定: act | act-with-mitigation | don't-act + 理由
```

### 每一栏为什么存在

| 栏位 | 它拦截的失败模式 |
| --- | --- |
| 动作 | 动作写得含糊（"清理一下"）就无法评估后果 |
| 受影响实体 | 不具名就无法推演二阶；"系统"不是实体 |
| 触发规则 | 不知道哪条规则在推，就不知道它在消耗什么 |
| 该规则读取的量 | 规则看的是 A，你查的是 B —— 这是最常见的假核对 |
| 我核对过的量 | 强制把"我以为我查了"变成"我查的是这个" |
| 二阶 | 跳过直接后果，直接想最终结果，导致漏掉中间成本 |
| 三阶 | 二阶的受害者会反应；反应本身有代价 |
| 不可逆性 | 可逆动作不需要门；不可逆动作必须过门 |
| 反事实 | 不比较就没有"值不值得" |
| 决定 | 三选一，禁止"再看看"这种非决定 |

**"该规则读取的量" vs "我核对过的量" 是本模板的核心。**
两者不一致 → 你的核对是无效核对，必须重做。

---

## 校验器会怎么判「我核对过的量」

这一栏必须写成 **`命令` → `输出`** 的形式，例如：

```
- 我核对过的量: `du -sh /srv/archive/2023` → 412G  /srv/archive/2023
```

判定规则（按严重度递增）：

| 你写的 | 校验器报的 | 结果 |
| --- | --- | --- |
| 「我确认过了，检查通过」 | `DEC-FAKE-CHECK` | 失败——纯声明式不是核对 |
| 只有描述没有命令 | `DEC-CHECK-NOCMD` | 失败——无法复核 |
| 有命令没有输出 | `DEC-CHECK-NOOUT` | 失败——只说查过不算查过 |
| 命令没在账本里出现过 | `LEDGER-NO-CALL` | 失败——证据不是运行时产生的 |
| 输出与账本记录不一致 | `LEDGER-OUTPUT-MISMATCH` | 失败——疑似改写或编造 |
| 命令与输出都对得上 | —— | 通过 |

**「启发式警告永不判失败」。** 若你的命令用了不同措辞（例如规则说"磁盘水位百分比"、
你写 `df -h`），校验器可能提示 `DEC-CROSS-HEURISTIC`，但那只是提示，
**不会**因此判你失败——它宁可漏报，也不误杀诚实的核对。

## 两个示例

> **下面两个示例写在代码围栏里，是文档，不是留档。**
> 校验器只解析围栏外的正文，所以抄示例不会通过——
> v1 把示例当真回归用例内嵌，于是「抄一遍模板示例」就能过，测的是示例不是表单。

```markdown
## 示例 1：核对通过，放行

## 决策 1 @ 2026-10-24T14:20:11Z
- 动作: 删除 /var/tmp/build-cache 下超过 7 天的缓存目录
- 受影响实体: ci-runner-03 上的 build-cache（唯一使用方：nightly-build 流水线）
- 触发规则: R-07 磁盘水位 > 85% 时清理陈旧缓存（推动 disk_freed_mb 计数）
- 该规则读取的量: du -sb /var/tmp/build-cache 的 7 天前分片大小
- 我核对过的量: `find /var/tmp/build-cache -maxdepth 1 -mtime +7 -type d | wc -l` → 4；
  且 `lsof +D /var/tmp/build-cache` 无进程占用
- 二阶: 4 个目录消失 → ci-runner-03 释放约 2.1GB → 磁盘水位从 91% 降到 84%
- 三阶: nightly-build 下次运行需全量重建（约 6 分钟）→ 但 7 天内它没有引用过这些目录，
      故无额外重建
- 不可逆性: 不可逆（删除），但对象是缓存 —— 可由构建重新生成，撤销成本 = 一次全量构建
- 反事实: 什么都不做 → 磁盘继续涨到 95%，夜间构建会因 ENOSPC 失败；
          最小替代（只删 2 个最大目录）→ 释放 1.1GB，水位 88%，仍高于阈值
- 决定: act —— 核对量与该规则读取的量一致（4 个目录 / 7 天 / 无占用），
        撤销成本（6 分钟重建）远低于不作为的失败成本（夜间构建挂掉）

**为什么通过**：核对量 = 规则读取量；三阶推演给出了具体的下游实体（nightly-build）
与可量化的成本（6 分钟）；反事实给出了不作为的后果（ENOSPC）；决定与推演一致。

---

## 示例 2：门拦住动作

## 决策 2 @ 2026-10-24T14:41:52Z
- 动作: 对 production 执行 `ALTER TABLE orders DROP COLUMN legacy_status`
- 受影响实体: orders 表（约 4.2 亿行）、billing-worker 服务、历史报表 job
- 触发规则: R-11 schema 收敛，清理标注 deprecated ≥ 90 天的列（推动 deprecated_cols 计数）
- 该规则读取的量: schema_meta.deprecated_since（legacy_status = 2026-07-02，已 114 天）
- 我核对过的量: `psql -c "select count(*) from schema_meta"` → 420000000；
      但**没有**查代码引用
- 二阶: 列消失 → billing-worker 的 3 处 INSERT 语句立即报错 → 结算队列积压 4.2 万笔
- 三阶: 积压 → 结算延迟 → 触发对账告警 → 财务侧人工介入（SLA 24h）
- 不可逆性: 不可逆。`DROP COLUMN` 在 PG 中丢弃数据，回滚需从备份恢复（RPO 1 小时）
- 反事实: 什么都不做 → deprecated_cols 计数不降，但无功能影响；
          最小替代：先 `ALTER TABLE ... SET UNUSED`（保留数据，可逆），观察 7 天
- 决定: don't-act —— 门拦住。核对量只是规则读取量的一部分，
        规则真正该消费的是「deprecated 且无代码引用」，而后者我没查。
        改为先执行 SET UNUSED 的最小替代。

**为什么拦住**：`我核对过的量` 是规则读取量的**子集**；二阶推出了具名实体与连锁成本；
指出风险后动作必须改变 —— 这里从 `act` 改成了 `don't-act` + 最小替代。
```

## 常见错误

| 错误 | 症状 | 修法 |
| --- | --- | --- |
| 假核对 | 只写「我确认过了」没有命令与输出 | 补上 `命令` → `输出` |
| 空泛实体 | `受影响实体: 系统` | 具名：服务名、表名、主机名、账户 id |
| 二阶当三阶 | 二阶写"最终结果" | 二阶必须是**直接**后果；三阶才是反应 |
| 有风险无动作变化 | 二阶写了成本，决定仍 `act` 无缓解 | 改成 `act-with-mitigation` 或 `don't-act` |
| 事后补写 | 时间戳晚于动作时间 | 门的意义在于事前；事后补写不算通过 |
| 无决定 | `决定: 再看看 / 待定` | 只允许三个值之一 |
| 否定式决定 | `决定: 不能 act` | 写 `don't-act`；带否定词的决定栏无法解析 |
| 推演灌水 | 二阶写「无任何后果，一切照旧」 | 二阶必须点名实体 + 给出数字 |
