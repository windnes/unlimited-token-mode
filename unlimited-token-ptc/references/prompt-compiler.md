# 把需求编译成 PTC 版提示词

把任意需求编译成「无限tokenPTC版提示词」。六步，每步有产物。

标准版的五步（提取歧义 → 消歧 → 外置记账 → 删掉稀缺感 → 写收工判据）在 PTC 里全部保留，
但第 3 步的含义变了，并且中间插入一步：**切程序边界**。

原因一句话：标准版把循环赶到 bash 脚本里，所以「外置记账」= 找一个脚本；
PTC 里循环本来就在程序里，所以「外置记账」= 找一块**磁盘**，而「切程序边界」= 决定**哪些事该在同一个程序里**。

**核心原则**：不要写「请小心 / 请高效 / 请注意风险」。要写**可验证的约束**。
实测：泛泛提醒（`v3-prompt`）均分 2226，在噪声内，缺陷一个没修；而把规则写死（`v1-clear`）是 2396。

---

## 第 1 步 · 提取歧义

扫需求文本，标记所有**可多种读法**的片段。命中以下任一即标记：

| 触发词 | 例子 | 两种读法 |
|---|---|---|
| 数量 + 未写对象 | 「最多 2 次」 | 2 次什么？调用？方向？周期？ |
| 「不同 / 相同」 | 「5 件不同的东西」 | 5 个 SKU？还是 5 个品类？ |
| 「默认 / 正常 / 一般」 | 「默认配置」 | 哪个默认？谁的默认？ |
| 「及时 / 尽快 / 适当」 | 「及时处理」 | 几秒？几轮？ |
| 「保留 / 退回」+ 未写时点 | 「可以退货」 | 只能退刚开的？还是以前的？ |
| 「最多 / 至少」+ 未写单位 | 「最多 2 个」 | 个什么？ |
| 阈值未写比较方向 | 「超过 80%」 | >80 还是 >=80？ |
| 未写失败处理 | 「重试」 | 重试几次？失败后停还是跳过？ |
| **PTC 专属**：未写程序边界 | 「改完跑测试再提交」 | 一个程序？三个程序？ |
| **PTC 专属**：未写超时 | 「等用户确认后继续」 | `timeoutMs` 多少？默认 120000 会杀掉提问 |

**产物**：歧义清单，每项两栏——`读法 A` / `读法 B`。

> 实测：一句「最多 2 次/周期」让 1017 **9/9 局**读成「每绿灯组最多 2 个动作」，
> **18/18 周期**全错，且**一次都没想过去核实**。不要指望它问。

---

## 第 2 步 · 消歧

每一项三选一：

1. **问** —— 值得问、且问了能改结果。一次问完，≤3 个问题，每个自带推荐答案。
2. **写死** —— 你能决定。直接写进需求，**不要留「合理即可」**。
3. **记为假设** —— 无法问也无法定。写进假设清单，标明「若此假设错，哪些结论失效」。

**禁止**：留空让它「自行判断」。

**写法对照**：

| 别写 | 改写 |
|---|---|
| 最多 2 次 | 每周期最多调用 2 次 `check_phase`，每周期刷新，未用即作废 |
| 5 件不同的东西 | 5 件不同商品；同品类的两件商品算不同商品 |
| 可以退货 | 结账前可退购物车内任意未封存商品，包括早先购买的 |
| 及时处理 | 每轮开始先处理「再不处理就会升级」的项，其余按 FIFO |
| 高效完成 | （删掉，见第 5 步） |
| 有问题就问我 | 有歧义时用 `ask_user_question`，该程序 `timeoutMs: 600000`，只返回回答不动手 |

PTC 专属的消歧：**「要不要问」必须同时决定「问的那个程序超时多少」**。
`ask_user_question` 也是程序内调用，人回答慢于 `timeoutMs`（默认 `120000`）就把整个程序杀掉，
回答丢失，模型随后按默认读法继续动手。所以任何含提问的程序，`timeoutMs` 写 `600000`。

## 第 3 步 · 外置记账

找出需求里所有**需要跨步保持的量**，逐个指定归属。PTC 里只有三种合法归属，**没有第四种**：

| 量 | 归属 | 怎么写 |
|---|---|---|
| 循环次数 | **程序内 `for`** | 「用一个程序跑 `for` 循环，每轮把一行 JSON 追加写 `state/iter.jsonl`」 |
| 预算 / 配额用量 | **状态文件** | 「每步开头读 `state/run.json` 的 `checks_spent`，不凭记忆」 |
| 进度 / 已完成项 | **状态文件（追加）** | 「追加写 `state/progress.jsonl`，一行一项」 |
| 剩余时间 / 时限 | **`timeoutMs`（真实数字）** | 「该程序 `timeoutMs: 600000`，超时即视为未完成」 |
| 重试计数 | **状态文件** | 「重试次数写 `state/run.json` 的 `retry_count`，每次 +1 并自增 `_rev`」 |
| 大块中间输出 | **磁盘文件** | 「先 `> state/raw.log 2>&1` 落盘，再 `tail -n 40` 分段读」 |

**绝对不要写**：「先查一次状态」「记住当前值」「在变量里累加」「跑完自己统计」。
最后一条在 PTC 里特别容易犯：`let n = 0; n++` 看起来像账本，其实程序一结束就没了
（`per-call` 下每次 `run_code` 是全新 VM；`persistent-in-memory` 下变量活着但模型看不见、
无 `_rev`、无并发保护）。**变量不是状态，磁盘才是。**

> 实测：「先查一次状态」让通过率 **6/6 → 4/6**，2/6 局耗尽预算。
> 原话判定：**「一个过时的锚点比没有锚点更危险」**。

---

## 第 4 步 · 切程序边界

这一步是 PTC 版新增的。产出一张**程序清单**：把任务切成一个个「一句话说得清意图」的程序。

### 判断标准

> **这个程序的 `description` 能不能写成一句 5–10 词的话（中文 8–40 字）？**

写不出来就说明这个程序装了多个意图，拆。

### 切分规则

| 规则 | 理由 |
|---|---|
| 一个程序一个意图 | `description` 与 `sandbox_permissions` 都是程序级字段，粒度越细审查信息越完整 |
| 一个程序最多一个不可逆动作 | `sandbox_permissions` 按整个程序授予，两个破坏性动作 = 权限被整段放大（缺陷 P5 捆绑不可逆） |
| 提问单独成程序 | 超时被杀时回答丢失；且提问程序只返回回答不动手（契约 1） |
| 先读状态，再写 | 每个写程序开头重读 `state/run.json`，不从记忆推导 |
| 长流程分段 | 每段证据先落盘，再跑下一段（缺陷 P6 截断即完成） |
| 只读查询可合并并发 | 只读调用可 `Promise.all`；写调用串行、按提交顺序 |

### 产物形状

> 下表 `P<n>` 是**程序编号**（与 `program-log.md` 的 `## 程序 <n>` 一致），
> 与缺陷编号 `P1–P7` 是两套体系。提到缺陷时写「缺陷 P5」，提到程序时写「程序 P5」。

| 程序 id | description（5–10 词） | 不可逆动作数 | 读写状态 | 超时 |
|---|---|---|---|---|
| P1 | 读取运行状态并返回当前阶段 | 0 | `state/run.json` 只读 | `120000` |
| P2 | 写入补丁并返回文件差异 | 0 | `src/a.ts` 写；`_rev` 不变 | `120000` |
| P3 | 运行测试并原样返回证据 | 0 | 无 | `600000` |
| P4 | 提交改动并返回提交哈希 | 1 | `state/run.json` `_rev` 7 → 8 | `120000` |

不可逆动作数不为 0 的程序，必须配一份决策块（见 `consequence-gate.md`），
且 `description` 里要点名那个动作。

### 常见切错

| 症状 | 例子 | 修法 |
|---|---|---|
| `description` 里有「并」「然后」「顺便」 | `"读状态并改文件并跑测试"` | 拆 |
| 一个程序两个 `rm` / 两次 `git push` | 批量删除 + 部署 | 必须拆 |
| 提问与动手同程序 | 问完就 `rm -rf` | 提问程序只 `return` 回答 |
| 把「省往返」当理由合并 | 三个写操作塞一个程序 | 往返不是成本，`run_code` 没有调用次数预算 |

## 第 5 步 · 删掉稀缺感

逐条删除以下措辞（它们会让它**用减少核对来省钱**，而不是用减少浪费）：

```
节省一点 · 别浪费 · 能一次做完就别分两步 · 别做多余的事
注意成本 · 控制开销 · 简洁优先 · 别啰嗦 · 只做必要的
简单看一下就行 · 快速验证一下
```

同族里还有一类更隐蔽的：把「剩余次数 / 剩余额度 / 还剩几步」写进提示词。
它不出现上面的字眼，但效果一样——制造紧张感，于是被砍掉的第一项永远是核对。

如果确实有硬限制，**写清真实数字和真实代价**：

```
✅ 该程序 timeoutMs: 600000（默认 120000、上限 600000）；超时即视为未完成，必须重新分段。
✅ 单次 run_code 输出上限 67108864 字节（64 MiB），超出即截断；大输出先落盘再分段读。
❌ 时间有限，请节约使用。
```

差别：前者让它知道**不用就废了**（超时就是失败），后者让它以为**用了就亏了**。

> 实测校准：所谓「抠门」在仓库里被拆成两半——
> **囤积会刷新的额度：不成立**（利用率 0.98–1.00，无空转周期）；
> **核对要钱就少做：成立**（问一次 1 元，8/8 → 5/8）。
> 所以这里删的是「制造稀缺感」，不是「禁止设限」。

PTC 专属补充：**不要写「省点调用」**。`run_code` 没有调用次数预算，
真正的上限是 `timeoutMs`（`600000`）、`maxOutputBytes`（`67108864`）、
`maxPendingCalls`（`128`）、`maxMessageBytes`（`134217728`）——这些是**真实数字**，写它们。

## 第 6 步 · 写收工判据

每条判据必须**可执行、可失败**，并且**证据必须来自 `return`**（只有 `return` 与 `console.log` 进对话）。

| 别写 | 改写 |
|---|---|
| 确保功能正常 | 运行 `npm test`，`return` 里 `exit: 0` 且输出含 `Tests: 42 passed` |
| 数据要正确 | 对 3 个样本逐字段比对源文件，`return` 里 diff 为空且附命令 |
| 处理完毕 | `state/progress.jsonl` 行数 == 输入行数，且无 `"status":"error"` |
| 性能要好 | `bench.sh` 的 p99 < 200ms，`return` 里贴出原始输出片段 |

**判据数量 = 验收项数量**，一条判据对应一条命令 + 一次真实输出。
判决由**读报告的人**根据 `exit` 与原始输出作出，不由程序自己宣布 `pass: true`。

每条判据还要写一句**可失败性**：如果实现错了，这条证据会怎么变红。
写不出可失败性的判据，不是判据。

## 编译后的骨架

```markdown
# 任务：<一句话，可量化>

## 契约摘要
- 歧义：已消歧，见下表；无待定项
- 状态：账本在 `state/run.json`（含 `_rev`）与 `state/events.jsonl`，不在程序变量里
- 门：每个不可逆动作一个程序 + 一份决策块（含 `程序 id` / `description` / `程序内不可逆动作数`）
- 核对：只读调用可并发，写调用串行；核对输出用 `return` 带回
- 信号：`timeoutMs` / `maxOutputBytes` / `ToolCallError` 都是事后信号，不作事前保护
- 预算：见「预算」节，全部是真实数字
- 收工：每条判据对应一条命令 + 一次真实输出，`return` 原始证据

## 程序边界规则
- 一个程序一个意图；`description` 是主动语态 5–10 词（中文 8–40 字），不含「并」「然后」「顺便」
- 一个程序最多一个不可逆动作，且它必须出现在 `description` 里
- 提问程序：`timeoutMs: 600000`，只 `return` 回答，不动手
- 每个写程序开头重读 `state/run.json`；写回时 `_rev + 1`，写前重读、不一致则重算不覆盖
- `Promise.all` 只放只读调用；`write` / `edit` / 有副作用的 `bash` 一次一个 `await`

## 程序清单
| 程序 id | description | 不可逆动作数 | 读写状态 | timeoutMs |
|---|---|---|---|---|
| P1 | <...> | 0 | <...> | 120000 |

## 状态文件
- `state/run.json` —— 单值状态：`phase`、`checks_spent`、`_rev`、`updated_at`
- `state/events.jsonl` —— 追加型事件，一行一个，只增不改
- `state/evidence/<stage>.json` —— 每段证据先落盘，供超时后取证
- `state/decisions.md` —— 决策块，只追加

## 证据要求
- 每个程序的 `return` 带 `cmd` / `exit` / `stdout` / `truncated`
- 输出可截断但不可改写；截断保留头尾，并标 `truncated: true`
- 禁止 `return { ok: true }` 这类孤立判决
- 每一处 `catch` 必须 `throw` 或 `return` 带 `exit: 1` 的对象（含 `toolName` / `message`）

## 完成判据
- [ ] <判据 1> → 验证：`<命令>`，期望：<真实可比对的输出>；可失败性：<会怎么变红>
- [ ] <判据 2> → 验证：`<命令>`，期望：<...>；可失败性：<...>

## 歧义决议
| 词 | 读法 | 采用 | 理由 |
|---|---|---|---|

## 假设（若错则失效）
- <假设> → 若错，<哪些判据失效>

## 工具与代价
| 工具 | 代价 | 备注 |
|---|---|---|
| `read` / `grep` / `glob` | 免费、可并发 | 核对的主力 |
| `bash`（只读，如 `git status`、`--dry-run`） | 免费、可并发 | 不可逆动作前必用 |
| `bash`（有副作用） | 串行、需 `description` 点名 | 一个程序最多一个不可逆动作 |
| `ask_user_question` | 一次往返，人可能慢 | 该程序 `timeoutMs: 600000` |
| `present` / `send_message` | 外部可见 | 视为不可逆，需决策块 |

## 状态归属
- 循环：程序内 `for`，每轮追加写 `state/iter.jsonl`；不靠变量计数
- 账本：`state/run.json`，每次写前重读、`_rev + 1`
- 证据：`return` 原始输出；大输出先落盘到 `state/raw.log` 再分段读
- 环境：`per-call` 下变量不跨调用存活；`persistent-in-memory` 下变量存活但不可见、无 `_rev`、无并发保护

## 预算
- `timeoutMs`：默认 `120000`，上限 `600000`；含提问的程序写 `600000`
- 单次输出：`maxOutputBytes` `67108864`（64 MiB）
- 单条消息：`maxMessageBytes` `134217728`（128 MiB）
- 待处理调用：`maxPendingCalls` `128`
- 堆上限：`maxOldGenerationSizeMb` `512`
- 优雅退出：`graceMs` `3000`
- 工具调用次数：不设人为上限。触顶情形只有上面这几个真实数字；触顶时按
  ① 不可逆动作前的核对 ② 完成判据验证 ③ 状态读取 ④ 探索试错 ⑤ 措辞打磨 的顺序花

## 禁止
- 不得在无核对的情况下断言「不可行 / 没有可选项」
- 不得把事后通知、`timeoutMs`、`maxOutputBytes` 当作事前保护
- 不得在未点名实体的情况下声称「已评估风险」
- 不得 `catch {}` 后继续；不得 `return { ok: true }` 作为判决
- 不得把计数、预算、进度存在程序变量里当账本
- 不得在一个程序里放两个不可逆动作
- 不得在 `description` 里写「cleanup / 整理 / 处理」而不点名动作

## 快速检查
- [ ] 每个数字都写了对象和单位
- [ ] 每个「可以 / 允许」都写了时点和边界
- [ ] 每个跨步量都有归属（程序内 `for` / 状态文件 / `timeoutMs`）
- [ ] 每个程序都能用一句 5–10 词说清意图
- [ ] 每个不可逆动作单独成程序，且出现在 `description` 里
- [ ] 含提问的程序写了 `timeoutMs: 600000`
- [ ] 提示词里没有任何稀缺感措辞
- [ ] 每条完成判据都能失败，且证据来自 `return`
- [ ] 没有任何「先查一次状态」「记住当前值」
```

## 完成判据

判据写完后逐条问三句：**这条命令能跑吗？跑完的 `exit` 和输出长什么样？实现错了会怎么变红？**

三句有一句答不上，这条判据不合格。判据与验收项一一对应，不多不少。

## 歧义决议

每项一行：`词` / `读法 A` / `读法 B` / `采用` / `理由`。
`采用` 栏不许写「视情况」；`理由` 栏不许写「惯例如此」。

## 假设

每条假设都要带失效范围：「若此假设错，判据 2、3 失效」。
没有失效范围的假设不是假设，是隐患。

## 工具与代价

只列真实会用到的工具，名字只用这些：
`bash`、`pwsh`、`read`、`write`、`edit`、`grep`、`glob`、`todo_write`、
`ask_user_question`、`present`、`subagent`、`send_message`。
不要发明工具名，也不要写「某个检查工具」。

## 状态归属

每个跨步量写清三件事：**存在哪个文件、谁负责更新、`_rev` 怎么变**。
写不出来的量，说明它其实不需要跨步，删掉。

## 预算

写真实数字，不写形容词。上面骨架里的六个数字来自运行时规格，直接抄。
工具调用次数不设人为上限——`run_code` 没有次数预算，编一个只会制造稀缺感。

## 禁止

禁止清单要能对着代码检查。写「注意安全」不算禁止项，写「不得 `catch {}` 后继续」才算。

## 快速检查

编译完扫一遍上面那份清单。任何一条打不上就回去改提示词，不要在交付物里解释。
