# 后果推演门（PTC 版）

契约 3 的完整操作手册。用于**任何不可逆动作之前**：提交、删除、发布、下单、放行、改配置、对外发消息。

标准版的门检查「动作 → 二阶 → 三阶」。PTC 版多一层：

> **程序边界就是门边界。**

因为 `run_code` 的 `sandbox_permissions` 是**整个程序**的属性，不是单次调用的属性。
一个程序里只要有一步破坏性动作，整段代码就在那个权限下执行；审查者看到的也只是一段整体。

---

## 为什么 PTC 需要额外的门

### 1. `sandbox_permissions` 是整个程序的属性

`run_code` 的参数里有 `sandbox_permissions` 与 `justification`，它们修饰的是**这一次程序**。
程序里第 1 行 `read`、第 5 行 `write`、第 9 行 `rm -rf` 拿到的是同一个权限档。

于是出现一种标准版不存在的绕过方式：

```ts
// 反例 —— 破坏性动作夹在良性步骤里，description 只写良性那半
const st = JSON.parse(String(await tools.read({ path: "state/run.json" })));
await tools.write({ path: "state/run.json", content: JSON.stringify({ ...st, phase: "cleanup" }) });
await tools.bash({ command: "rm -rf build/ cache/", description: "清理临时目录" });
return { ok: true };
```

`description` 写「更新运行阶段」也完全说得通——前半段确实是。而 `rm -rf` 就在同一个权限下执行了。
**这就是偷偷提权：提的不是权限档，是「审查注意力」。**

### 2. `description` 是模型自己写的

`description` 必填、主动语态 5–10 词，但**内容由写程序的人决定**。
写「整理一下」「cleanup」「更新状态」就能让一次删除看起来像维护。
标准版里命令本身就在 bash 文本里，`rm -rf` 跑不掉；PTC 里命令藏在程序内部，
外部只看得到 `description`。

所以门必须**同时**约束两件事：程序里最多几个不可逆动作，以及 `description` 有没有点名它。

### 3. 门的三个新栏位就是为此存在的

| 新栏位 | 拦的东西 |
|---|---|
| `程序 id` | 让决策块能对上程序账本（`program-log.md` 的 `## 程序 <n>`），事后可归因 |
| `description`（原样） | 强制把提交给审查的那句话抄进门里，写含糊就当场露出来 |
| `程序内不可逆动作数` | 一个整数。≥2 直接判不过门，必须拆程序 |

---

## 固定块格式

逐字使用下面这个形状。字段名不改、顺序不改、不合并。

```
## 决策 <n> @ <ISO 时间>
- 程序 id: P<n>
- description: <run_code 的 description 原样，主动语态 5–10 词；中文 8–40 字>
- 程序内不可逆动作数: <整数>
- 动作: <我即将做什么>
- 受影响实体: <具名实体>
- 触发规则: <规则 id + 它推动哪个计数>
- 该规则读取的量: <规则消费的那个变量>
- 我核对过的量: <我实际检查的那个变量>
- 二阶: <规则触发 -> 哪个实体 -> 什么成本>
- 三阶: <该实体的反应 -> 导致什么>
- 不可逆性: <可逆？撤销成本？>
- 反事实: <什么都不做 / 最小替代 -> 差异>
- 决定: act | act-with-mitigation | don't-act + 理由
```

标准版十一栏 = 决策标题行（`## 决策 <n> @ <时间>`）+ 十栏正文（动作 / 受影响实体 / 触发规则 /
该规则读取的量 / 我核对过的量 / 二阶 / 三阶 / 不可逆性 / 反事实 / 决定），全部原样保留；
PTC 版新增三栏（程序 id / description / 程序内不可逆动作数），共十四栏。

> 编号提示：`程序 id` 用的 `P<n>` 是**程序编号**（与 `program-log.md` 一致），
> 与缺陷编号 `P1–P7` 是两套体系。提到缺陷时一律写「缺陷 P5」，提到程序时写「程序 P5」或 `程序 id: P5`。

### 每一栏为什么存在

| 栏位 | 它拦截的失败模式 |
|---|---|
| **程序 id** | 决策与程序对不上号，事后无法回答「这个动作是哪段代码干的」。与 `program-log.md` 的 `P<n>` 同一编号体系 |
| **description（原样）** | 写「cleanup」「整理一下」就能绕过审查；抄进门里，含糊会当场暴露。它也是唯一进入审查视野的程序文本 |
| **程序内不可逆动作数** | ≥2 说明权限被整段放大（缺陷 P5 捆绑不可逆）。这个数字是拆分程序的触发器，不是形容词 |
| 动作 | 动作写得含糊（「清理一下」）就无法评估后果 |
| 受影响实体 | 不具名就无法推演二阶；「系统」不是实体 |
| 触发规则 | 不知道哪条规则在推，就不知道它在消耗什么 |
| 该规则读取的量 | 规则看的是 A，你查的是 B —— 这是最常见的假核对 |
| 我核对过的量 | 强制把「我以为我查了」变成「我查的是这个」 |
| 二阶 | 跳过直接后果、直接想最终结果，导致漏掉中间成本 |
| 三阶 | 二阶的受害者会反应；反应本身有代价 |
| 不可逆性 | 可逆动作不需要门；不可逆动作必须过门 |
| 反事实 | 不比较就没有「值不值得」 |
| 决定 | 三选一，禁止「再看看」这种非决定 |

**「该规则读取的量」vs「我核对过的量」是本模板的核心。** 两者不一致 → 你的核对是无效核对，必须重做。

**「程序内不可逆动作数」是本模板的第二个核心。** 它不为 0 时，`description` 必须点名那个动作；
它 ≥2 时，不要改这个数字，去**拆程序**。

### 过门流程

1. **判定不可逆性** —— 可逆且便宜：不过门。可逆但昂贵：只写二阶。不可逆：完整过门。
2. **点名实体** —— 不许写「某些请求」「部分用户」「这条车道」。推演里出现「某些 / 一些 / 部分 / 之类的」，视为**没过门**。
3. **找触发规则和它读的量** —— 「我这一步推动哪个计数器？该规则读哪个量？我刚核对的是哪个量？」第二个和第三个不一致，就是缺陷本身。
4. **写二阶 / 三阶** —— 代价能写成钱 / 时间 / 分数就写，不能写就写「不可量化，因为……」。
5. **反事实** —— 至少比较「不动」与「最小替代」两个选项。
6. **判** —— `act` / `act-with-mitigation` / `don't-act`，三选一。
   **禁止第四种答案：「已注意到风险，继续」。**

## 示例 1：门放行（可做）

下面这个块是**可被 lint 校验的裸块**（不在代码围栏里），`ptc_lint.py --kind decision` 应当通过。
它同时充当本模板的回归用例。

## 决策 1 @ 2026-10-24T14:20:11Z
- 程序 id: P12
- description: 清理超过七天的构建缓存目录
- 程序内不可逆动作数: 1
- 动作: 删除 /var/tmp/build-cache 下超过 7 天的缓存目录
- 受影响实体: ci-runner-03 上的 build-cache（唯一使用方：nightly-build 流水线）
- 触发规则: R-07 磁盘水位 > 85% 时清理陈旧缓存（推动 disk_freed_mb 计数）
- 该规则读取的量: du -sb /var/tmp/build-cache 的 7 天前分片大小
- 我核对过的量: `find /var/tmp/build-cache -maxdepth 1 -mtime +7 -type d | wc -l` → 4；
  且 `lsof +D /var/tmp/build-cache` 无进程占用；且 nightly-build 最近 7 天未引用这 4 个目录
- 二阶: 4 个目录消失 → ci-runner-03 释放约 2.1GB → 磁盘水位从 91% 降到 84% → 低于阈值
- 三阶: nightly-build 下次运行需全量重建（约 6 分钟）→ 但 7 天内它没有引用过这些目录，
  故无额外重建；若引用过，成本会体现在下一轮构建时长上
- 不可逆性: 不可逆（删除），但对象是缓存 —— 可由构建重新生成，撤销成本 = 一次全量构建
- 反事实: 什么都不做 → 磁盘继续涨到 95%，夜间构建会因 ENOSPC 失败；
  最小替代（只删 2 个最大目录）→ 释放 1.1GB，水位 88%，仍高于阈值
- 决定: act —— 核对量与该规则读取的量一致（4 个目录 / 7 天 / 无占用），
  撤销成本（6 分钟重建）远低于不作为的失败成本（夜间构建挂掉）

**为什么通过**：`程序内不可逆动作数` 是 1，且 `description` 里出现了「清理…目录」，与动作一致；
核对量 = 规则读取量；三阶给出了具体的下游实体（nightly-build）与可量化的成本（6 分钟）；
反事实给出了不作为的后果（ENOSPC）；决定与推演一致。

对应的程序（`description` 必须与上面那栏逐字一致，`sandbox_permissions` 只授予这一个程序）：

```ts
// 程序 P12 —— 调用 run_code 时 description 与决策块逐字一致
const find = await tools.bash({
  command: "find /var/tmp/build-cache -maxdepth 1 -mtime +7 -type d",
  description: "列出超过七天的缓存目录",
});
const dirs = String(find?.stdout ?? "").split("\n").filter(Boolean);

for (const d of dirs) {
  // 写操作串行，一次一个；不放进 Promise.all
  await tools.bash({ command: `rm -rf ${JSON.stringify(d)}`, description: "删除单个陈旧缓存目录" });
}

const after = await tools.bash({ command: "df -h /var/tmp", description: "读取删除后磁盘水位" });
return [
  { cmd: "find /var/tmp/build-cache -maxdepth 1 -mtime +7 -type d", exit: 0, stdout: dirs.join("\n"), truncated: false },
  { cmd: "df -h /var/tmp", exit: 0, stdout: String(after?.stdout ?? ""), truncated: false },
];
```

## 示例 2：门拦下（不可做）

## 决策 2 @ 2026-10-24T14:41:52Z
- 程序 id: P13
- description: 删除废弃列并同步更新计费服务
- 程序内不可逆动作数: 2
- 动作: 对 production 执行 `ALTER TABLE orders DROP COLUMN legacy_status`，并改 billing-worker 的 3 处 INSERT
- 受影响实体: orders 表（约 4.2 亿行）、billing-worker 服务、历史报表 job
- 触发规则: R-11 schema 收敛，清理标注 deprecated ≥ 90 天的列（推动 deprecated_cols 计数）
- 该规则读取的量: schema_meta.deprecated_since（legacy_status = 2026-07-02，已 114 天）
- 我核对过的量: 我查了 deprecated_since = 114 天 ✓；但**没有**查 `pg_stat_user_tables` 之外的代码引用
- 二阶: 列消失 → billing-worker 的 3 处 INSERT 语句立即报错 → 结算队列积压
- 三阶: 积压 → 结算延迟 → 触发对账告警 → 财务侧人工介入（SLA 24h）
- 不可逆性: 不可逆。`DROP COLUMN` 在 PG 中丢弃数据，回滚需从备份恢复（RPO 1 小时，
  即最多丢 1 小时的订单变更），且恢复期间 orders 表只读
- 反事实: 什么都不做 → deprecated_cols 计数不降，但无功能影响（该列已无写入）；
  最小替代：先 `ALTER TABLE ... SET UNUSED`（保留数据，可逆），观察 7 天，确认无引用后再真正 DROP
- 决定: don't-act —— 门拦住。两个原因：一是 `程序内不可逆动作数` 为 2（DROP 列 + 改服务代码），
  权限被整段放大；二是核对量（deprecated_since）只是规则读取量的一部分，
  规则真正该消费的是「deprecated 且无代码引用」，而后者我没查。
  改为拆成两个程序：先执行 SET UNUSED 的最小替代，并在下一块决策里记录观察结果

**为什么拦住**：两处独立失败同时出现。`程序内不可逆动作数: 2` 说明这个程序从一开始就不该存在——
`DROP COLUMN` 与改服务代码是两件事，`sandbox_permissions` 却只授予一次、`description` 只写了一句。
另外 `我核对过的量` 是规则读取量的**子集**（只查了时间，没查引用），二阶推出了具名实体
（billing-worker）与不可逆的恢复成本。**指出风险后动作必须改变**——这里从 `act` 改成
`don't-act` + 拆程序 + 最小替代。

## 常见错误

| 错误 | 症状 | 修法 |
|---|---|---|
| **一个程序两个 DROP** | `程序内不可逆动作数` ≥ 2 | 拆程序。不要改数字，改代码 |
| **`description` 写 cleanup** | `description` 是「整理一下」「清理」「更新状态」，动作栏却有删除/发布/提交 | 重写 `description` 点名真实动作，或把破坏性步骤拆出去单独成程序 |
| **`description` 与动作不一致** | 门里抄的 `description` 和代码实际干的事不同 | 逐字重抄；不一致就是缺陷 P5，先改程序 |
| 假核对 | `该规则读取的量` 与 `我核对过的量` 不同 | 重查，直到两者一致或明确记录差异理由 |
| 空泛实体 | `受影响实体: 系统` | 具名：服务名、表名、主机名、账户 id |
| 二阶当三阶 | 二阶写「最终结果」 | 二阶必须是**直接**后果；三阶才是反应 |
| 有风险无动作变化 | 二阶写了成本，决定仍 `act` 无缓解 | 改成 `act-with-mitigation` 或 `don't-act` |
| 事后补写 | 时间戳晚于动作时间 | 门的意义在于事前；事后补写不算通过 |
| 无决定 | `决定: 再看看 / 待定` | 只允许三个值之一 |
| 程序 id 对不上 | 决策块里的 `P13` 在程序账本里不存在，或编号重复 | 与 `program-log.md` 用同一编号体系，一个程序一个 id |

## 与其他契约的衔接

- **与契约 1**：门里出现「按惯例来」「照默认处理」这种未消解的读法时，先回到 `ask_user_question`，
  提问程序显式设 `timeoutMs: 600000`，只返回回答不动手。
- **与契约 2**：门要求「我核对过的量」，而核对结果必须来自磁盘或工具返回，不能来自程序变量。
- **与契约 4**：核对不免费这条就走不通——PTC 里核对输出不进对话，结构性成本已降到最低，
  所以「太贵所以不查」没有立足点；唯一的新借口是 `catch {}` 吞掉。
- **与契约 5**：推演里出现「有通知会兜底」，先给通知打事前/事后标签。`timeoutMs` 与
  `maxOutputBytes` 都是**事后**信号，不能当作事前保护。
- **与契约 7**：决策块是收工报告的证据链，`don't-act` 的决策也要留档。

## 留档

每个不可逆动作一份决策块，追加写进 `state/decisions.md`（只追加，不改历史）。
收工前跑：

```bash
python scripts/ptc_lint.py state/decisions.md --kind decision --strict
```

校验器分两档：

| 档 | 检查什么 | 默认 | `--strict` |
|---|---|---|---|
| 硬 | 缺栏位、空值、占位符、`决定` 不是三选一、`程序内不可逆动作数` 不是整数、`程序 id` 缺失 | 失败 | 失败 |
| 软 | **疑似假核对**（`该规则读取的量` 与 `我核对过的量` 毫无共同点）、**实体没点名**（只有「系统 / 某些 / 部分」这类词）、**推演过简**（二阶/三阶一两句带过）、**`description` 疑似含糊**（只含「整理 / 清理 / 更新 / 处理」而无具体对象） | 警告，不改变退出码 | **失败** |

软检查是启发式的，可能误报，所以默认只警告；但在**严格档**任务里应当开 `--strict`。
它拦的正是这个模式最在意的两件事：**规则看的是 A，你查的是 B**；**程序干的是 C，你写的是 D**。
