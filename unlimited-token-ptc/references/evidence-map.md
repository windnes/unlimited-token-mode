# 证据地图（PTC 版）

七条契约的**实测数字继承标准版**：同一批基准、同一批数字、同一批变体 id，本文不改写、不四舍五入、
不重新解读。PTC 版**新增**的是另一类东西——**机制性证据**：来自 PTC 运行时本身的结构事实，
不是模型行为统计。

这个区别必须守住：

| | 标准版证据 | PTC 侧机制性证据 |
|---|---|---|
| 来源 | 公开 POV 基准的跑分与轨迹统计 | 运行时规格里的结构事实（工具面、输出通道、超时、权限授予粒度） |
| 形态 | 「多少局、多少次、百分比」 | 「因为运行时只把 X 送进对话，所以 Y 必然发生」 |
| 能否被一次新实验推翻 | 能（样本变大就可能变） | 不能（除非运行时改版） |
| 用途 | 证明「这个缺陷真实存在过」 | 证明「在 PTC 里它一定会再出现，除非硬规则挡住」 |

所以引用时的规矩是：**数字标标准版，机制标 PTC 侧**，不要把两者混成一句话。

## 继承自标准版的实测数字

被研究对象：`deepseek-v4.1-flash-1017`（下称 1017），对照组 `R19`（旧版），对照模型 `v4-pro`。
三个场景：超市盲盒（8 种子 × 8 变体）、路口日志复演与反事实（R19 / 1017 各 3 局，326/326 周期
逐周期对齐）、团队采购荷兰拍（正式轮 18/48 局，v4-pro 对照 3/16 局）。
路口基准分差背景：三局均值 1017 **567.98**，R19 **687.30**，差约 **119**。

### 契约 1 · 歧义契约

| 证据 | 数字 |
|---|---|
| 歧义句「最多 2 次/周期」被读成「最多 2 个方向/周期」 | **9/9** 局、**18/18** 周期全错，达成率 **0.26**，**一次都没想过去核实** |
| 同样任务、把限制的对象和单位写清 | v0 与 v4 均 **3/3** 局达成率 **1.00** |
| 盲盒把 4 处歧义全部写死 | 均分 **2154 → 2396（+242）**，封存打在垃圾上 **5/8 → 1/8** |
| 收益超过噪声 | +242 > v0 种子标准差的一半（**127**） |
| 它其实**会**问 | v0 免费店员 **8/8** 局都问，中位数 **2** 次；`wallet` 中位数 **3** 次 |
| 去掉工具名单和「免费」字样也照样问 | `v5-unmarked` **8/8** 局问，中位数 **2** |
| 没有可问的工具时，默认取**宽松**读法 | `v6-no-staff` 同品类留下 **8/8** |

结论：真正的损失不是「不问」，而是**问的内容不稳定**——歧义必须由使用方写死。

## PTC 侧的机制性证据

下面每一条都是**运行时结构事实**，不是跑分。它们的用法是：先承认事实，再推出硬规则。

### P3 · 摘要代替证据 —— 因为只有 `return` 与 `console.log` 进对话

`run_code` 的输出是 `{ logs: string[], result: json, sandbox: { mode, denied, enforcement } }`。
程序里的一切中间量——读到的文件、跑过的命令、拿到的退出码——**全部留在 VM 里，随程序结束丢弃**。
唯一穿过边界的，是 `return` 的值和 `console.log` 打印的字符串。

**所以硬规则是**：判决必须由**读者**根据 `return` 里的原始证据作出，程序不得只返回自己的结论。
返回 `{ ok: true }` 时，对话里除了这四个字符什么都没有——不是「证据不足」，是**零证据**。

### P2 · 自证判决 —— 同上，且 `result` 是 `json`

`result` 字段的类型就是 `json`：程序能把任何形状塞进去，包括 `{ allPass: true }`。
运行时不会替你校验它是否对应一次真实执行。

**所以硬规则是**：`return` 里禁止出现孤立的布尔判决；每个 `pass` 必须与 `exit` 或原始输出同框，
并且必须附一句**可失败性**（如果实现错了，这条证据会怎么变红）。

### P1 · 吞异常 —— 因为 `ToolCallError` 需要 `catch` 才能继续

失败的工具调用 reject 一个 `ToolCallError`（带 `toolName` 与 `message`）。
在程序里，reject 要么被 `catch` 接住、要么终止整个 `run_code`。`catch {}` 让它「不终止」——
于是程序继续往下跑，最终 `return` 一个成功形状的结果。运行时无法区分「工具成功」与「异常被吞」。

**所以硬规则是**：`catch` 块内必须 `throw`，或 `return` 一个带 `exit: 1` 且含 `toolName` / `message`
的对象。空 `catch` 与 `catch (e) { return { ok: true } }` 一律视为缺陷 P1。

### P6 · 截断即完成 —— 因为 `timeoutMs` 杀进程时程序内 `catch` 可能不跑

`timeoutMs` 默认 `120000`、上限 `600000`。超时时运行时终止整个程序——**进程被杀，不是抛异常**，
所以程序内 `try/catch` 不保证执行，`finally` 也不保证。`maxOutputBytes` 是 `67108864`（64 MiB），
超出部分直接不返回，程序对此没有感知。

**所以硬规则是**：证据必须**先落盘再继续**（`state/evidence/<stage>.json`），因为文件是唯一不依赖
「程序跑完」的载体。返回里的 `timedOut` 只描述「catch 跑到了」，已落盘证据才描述「哪段真的完成了」。
被截断的输出必须带 `truncated: true`。

### P5 · 捆绑不可逆 —— 因为 `sandbox_permissions` 按整个程序授予

`run_code` 的 `sandbox_permissions` 是**程序级**参数，不是调用级。一个程序里如果既有良性步骤又有
破坏性步骤，破坏性步骤拿到的是整段代码的权限；审查者看到的也只是一段整体。

**所以硬规则是**：一个程序最多一个不可逆动作；该动作必须写进 `description`（主动语态 5–10 词）；
决策块必须填 `程序内不可逆动作数`，且当它不为 0 时，`description` 必须点名那个动作。

### P4 · 隐式账本 —— 因为 `per-call` 变量不存活

默认执行模式 `per-call`：每次 `run_code` 是全新 VM，变量不跨调用存活。
`persistent-in-memory` 下变量跨调用存活，但**不可见、无版本、无并发保护**——模型看不到它，
它没有 `_rev`，两个分支同时改会互相覆盖。

**所以硬规则是**：账本只能落盘。`state/run.json` 存单值（含 `_rev`），`state/events.jsonl` 存追加事件。
任何「已经花了多少」的数字都必须来自磁盘读数，不能来自程序变量，也不能来自「我记得」。

### P7 · 并发读改写 —— 因为只读调用才允许 `Promise.all`

规格写明：只读调用可 `Promise.all` 并发，**写调用单独串行、按提交顺序**执行。
在同一个状态文件上并发读-改-写，两个分支读到同一份 `_rev`，各自 +1 再写回，结果只 +1。

**所以硬规则是**：`Promise.all` 里只放 `read` / `grep` / `glob` / 只读 `bash`；
所有 `write` / `edit` / 有副作用的 `bash` 都在 `Promise.all` 之外，一次一个 `await`。

### 契约 1 的 PTC 落点 —— 因为 `ask_user_question` 也是程序内调用

`ask_user_question` 在 PTC 里是 `await tools.ask_user_question(...)`。人回答慢于 `timeoutMs`
（默认 `120000`）就把整个程序杀掉，回答丢失——随后模型只剩默认读法，按默认读法继续动手。

**所以硬规则是**：含提问的程序显式写 `timeoutMs: 600000`；程序只**返回**回答，不在同一个程序里据此动手。

## 已被证伪的错误做法（别照着做）

八条。前四条来自标准版实测，后四条是 PTC 专属的机制性错误。**这些看起来都像解法。**

| 错误做法 | 实测结果 / 机制后果 |
|---|---|
| 「先查一次状态」写进提示词 | **有害**：4/6 提交、2/6 耗尽，过时锚点被当权威 |
| 把状态/余额塞进每个工具结果（`v2-harness`） | 均分 **1879** < v0 **2154**，封存缺陷**未修** |
| 泛泛提醒「注意风险 / 考虑后果」（`v3-prompt`） | **2226**，仍在噪声内，封存缺陷未修 |
| 让它复述规则 | **反效果**：它把**错误理解本身**复述了出来——「At most 2 per cycle：每绿灯组最多 2 个动作」 |
| **PTC**：用 `persistent-in-memory` 省掉状态文件 | 变量活着但**不可见**（只有 `return` / `console.log` 进对话）、无 `_rev`、无并发保护。省掉的是唯一可核对的账本，留下的是一个摸不到的影子（缺陷 P4） |
| **PTC**：把多个写操作塞进一个程序省往返 | 往返不是成本，`run_code` 没有调用次数预算；换来的是失败点不可定位 + `sandbox_permissions` 被整段放大（缺陷 P5 捆绑不可逆） |
| **PTC**：`catch {}` 之后继续，或 `return { ok: true }` 当判决 | `ToolCallError` 被吃掉、判决没有证据（缺陷 P1 吞异常 + 缺陷 P2 自证判决），且**无法从事后证据里恢复** |
| **PTC**：`Promise.all` 里并发改同一个状态文件 | 两个分支读到同一份 `_rev`，各 +1 再写回只 +1；`_rev` 失效且不报错（缺陷 P7） |

标准版里还有三条同样被证伪，本文不重复展开，直接列结论：

- **要求它报出心算余额**（`v4-belief`）：**1780**，反而更差；封存打在垃圾上 **7/8**。
- **用「风险厌恶 / 不核实」描述这个模型**：两条描述**都已被推翻**。
- **靠提示词修「观望 → 集中盲放」**：**不敏感**，8 个种子下均值 **−37.0 ~ 5.8**，SD **30–70**，全在噪声内。

## 未验证的推断（引用时必须标注）

以下都是**推断**，不是实测。写进交付物时必须带上「推断」二字，不能写成结论。

1. **「PTC 下契约 2 的失败率会上升」** —— 推断依据：标准版里漂移只在 40+ 轮出现，
   而 PTC 的 `per-call` 让变量每程序清零，理论上减少了「跨步心算」的机会，也减少了「程序内变量」
   被误当账本的机会。**两个方向都说得通，没有实验。**
2. **「一程序一意图能降低缺陷 P5 的发生率」** —— 推断依据：`description` 与 `sandbox_permissions` 都是
   程序级字段，粒度越细、审查信息越完整。但**没有对照实验**测量拆分前后的不可逆动作误授率。
3. **「`truncated: true` 会让人更少把截断当完成」** —— 推断依据：缺陷 P6 的失败是「感知不到截断」，
   显式标记应当修复感知。**未验证标记是否真的改变判断**。
4. **「`timeoutMs: 600000` 足以覆盖一次真实提问」** —— 推断依据：10 分钟远长于常见回答时间。
   **没有测量回答时间的分布**，长尾情形未知。
5. **「PTC 里契约 4 的收益比标准版更大」** —— 推断依据：核对输出不进对话（除非 `return`），
   核对的结构性成本已降到最低。**但「成本低」是否等于「会去核」，没有实验。**

## 引用准则

在交付物里引用本文件时：

- **数字必须带场景 + 变体 id**，例如「盲盒 `v1-clear`：2154 → 2396」「路口 1017 hold 周期未试算 73%」。
- **区分两类证据**：跑分数字标「标准版实测」，结构事实标「PTC 运行时规格」。
  不要写「实测证明 PTC 里必然吞异常」——那是机制推论，不是实测。
- **不要引用本文件里没有的数字。** 需要新数字时，标注「未测量」。
- **「未验证的推断」那一节的内容，引用时必须保留「推断」字样**，并说明缺少哪类实验。
- **已被证伪的做法**只能作为反例引用，不能作为建议。
- 提到 `per-call` / `persistent-in-memory` 时，写全模式名，不要简写成「内存模式」——
  这个区别是缺陷 P4 隐式账本的全部内容。
