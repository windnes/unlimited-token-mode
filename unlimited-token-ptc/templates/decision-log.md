# 决策日志（decision log）—— 无限tokenPTC版

> 契约 3（后果推演门）的载体。**每一个不可逆动作前写一个块，不是事后补。**
> 校验：`python scripts/ptc_lint.py <本文件> --kind decision`
> 严格校验：追加 `--strict`，把「疑似假核对 / 实体不具体 / 推演过简 / description 含糊」升级为失败。
>
> 核心禁令：**指出风险却不改变动作，等于没指出。** 若"二阶"栏写了真实成本，而"决定"栏仍是 `act` 且无缓解措施，此块无效。
>
> PTC 专属前提：`sandbox_permissions` 是按**整个程序**授予的，不是按动作授予的。
> 所以本模板新增三栏，把"这个动作发生在哪个程序里、那个程序还干了什么、那个程序有没有被提权"固定下来 ——
> 这是 P5（捆绑不可逆）唯一的拦截点。一个程序里塞两个不可逆动作，或破坏性动作没写进 `description`，
> 都属于**偷偷提权**：程序整体的授予范围被用来覆盖了未被点名的步骤。

---

## 固定块格式

```text
## 决策 <n> @ <ISO 时间>
- 动作: <我即将做什么>
- 程序 id: P<n>
- description: <原样粘贴该 run_code 的 description 参数>
- 程序内不可逆动作数: <整数>
- 受影响实体: <具名实体>
- 触发规则: <规则 id + 它推动哪个计数>
- 该规则读取的量: <规则消费的那个变量>
- 我核对过的量: <我实际检查的那个变量>
- 二阶: <规则触发 -> 哪个实体 -> 什么成本>
- 三阶: <该实体的反应 -> 导致什么>
- 不可逆性: <可逆？撤销成本？>
- 反事实: <什么都不做 / 最小替代 -> 差异>
- 决定: act | act-with-mitigation | don't-act + 理由
```

### 每一栏为什么存在

| 栏位 | 它拦截的失败模式 |
| --- | --- |
| 动作 | 动作写得含糊（"清理一下"）就无法评估后果 |
| 程序 id | 不知道动作落在哪个 `run_code` 里，就无法回查它的 `timeoutMs`、`sandbox_permissions` 与证据块 |
| description | `description` 是运行时唯一被记录的程序意图；含糊的 description 让提权范围与意图脱钩 |
| 程序内不可逆动作数 | 一个程序两个不可逆动作 = 拆不开的失败；这个数字 > 1 就必须拆程序 |
| 受影响实体 | 不具名就无法推演二阶；"系统"不是实体 |
| 触发规则 | 不知道哪条规则在推，就不知道它在消耗什么 |
| 该规则读取的量 | 规则看的是 A，你查的是 B —— 这是最常见的假核对 |
| 我核对过的量 | 强制把"我以为我查了"变成"我查的是这个" |
| 二阶 | 跳过直接后果，直接想最终结果，导致漏掉中间成本 |
| 三阶 | 二阶的受害者会反应；反应本身有代价 |
| 不可逆性 | 可逆动作不需要门；不可逆动作必须过门 |
| 反事实 | 不比较就没有"值不值得" |
| 决定 | 三选一，禁止"再看看"这种非决定 |

**"该规则读取的量" vs "我核对过的量" 是本模板的核心。** 两者不一致 → 你的核对是无效核对，必须重做。
**"程序 id" + "description" + "程序内不可逆动作数" 是 PTC 版新增的核心。** 三者必须互相自洽：
程序 id 指向的程序，其 `description` 必须点名本栏的"动作"；且该程序内不可逆动作数必须为 1。

## 示例 1：核对通过，放行

## 决策 1 @ 2026-10-24T14:20:11Z
- 动作: 删除 /var/tmp/build-cache 下超过 7 天的缓存目录
- 程序 id: P4
- description: 删除陈旧构建缓存目录
- 程序内不可逆动作数: 1
- 受影响实体: ci-runner-03 上的 build-cache（唯一使用方：nightly-build 流水线）
- 触发规则: R-07 磁盘水位 > 85% 时清理陈旧缓存（推动 disk_freed_mb 计数）
- 该规则读取的量: du -sb /var/tmp/build-cache 的 7 天前分片大小
- 我核对过的量: `find /var/tmp/build-cache -maxdepth 1 -mtime +7 -type d | wc -l` → 4；
  且 `lsof +D /var/tmp/build-cache` 无进程占用；且 nightly-build 最近 7 天未引用这 4 个目录
- 二阶: 4 个目录消失 → ci-runner-03 释放约 2.1GB → 磁盘水位从 91% 降到 84% → 低于阈值
- 三阶: nightly-build 下次运行需全量重建（约 6 分钟）→ 但 7 天内它没有引用过这些目录，
      故无额外重建；若引用过，成本会体现在下一轮构建时长上
- 不可逆性: 不可逆（删除），但对象是缓存 —— 可由构建重新生成，撤销成本 = 一次全量构建
- 反事实: 什么都不做 → 磁盘继续涨到 95%，夜间构建会因 ENOSPC 失败；
          最小替代（只删 2 个最大目录）→ 释放 1.1GB，水位 88%，仍高于阈值
- 决定: act —— 核对量与该规则读取的量一致（4 个目录 / 7 天 / 无占用），
        程序 P4 内只有这一个删除动作、`description` 已点名"删除陈旧构建缓存目录"，
        撤销成本（6 分钟重建）远低于不作为的失败成本（夜间构建挂掉）

**为什么通过**：核对量 = 规则读取量；三阶推演给出了具体的下游实体（nightly-build）与可量化的成本（6 分钟）；
反事实给出了不作为的后果（ENOSPC）；程序 P4 的 `description` 与"动作"栏指向同一件事，且程序内不可逆动作数 = 1；
决定与推演一致。

## 示例 2：门拦住动作

## 决策 2 @ 2026-10-24T14:41:52Z
- 动作: 对 production 执行 `ALTER TABLE orders DROP COLUMN legacy_status`
- 程序 id: P6
- description: 删除废弃列并清理索引
- 程序内不可逆动作数: 2
- 受影响实体: orders 表（约 4.2 亿行）、billing-worker 服务、历史报表 job
- 触发规则: R-11 schema 收敛，清理标注 deprecated ≥ 90 天的列（推动 deprecated_cols 计数）
- 该规则读取的量: schema_meta.deprecated_since（legacy_status = 2026-07-02，已 114 天）
- 我核对过的量: 我查了 deprecated_since = 114 天 ✓；
     但**没有**查 `SELECT count(*) FROM pg_stat_user_tables` 之外的代码引用
- 二阶: 列消失 → billing-worker 的 3 处 INSERT 语句立即报错 → 结算队列积压
- 三阶: 积压 → 结算延迟 → 触发对账告警 → 财务侧人工介入（SLA 24h）
- 不可逆性: 不可逆。`DROP COLUMN` 在 PG 中丢弃数据，回滚需从备份恢复（RPO 1 小时，
     即最多丢 1 小时的订单变更），且恢复期间 orders 表只读
- 反事实: 什么都不做 → deprecated_cols 计数不降，但无功能影响（该列已无写入）
         最小替代：先 `ALTER TABLE ... SET UNUSED`（保留数据，可逆），
         观察 7 天，确认无引用后再真正 DROP
- 决定: don't-act —— 门拦住。三处问题同时成立：
        (1) 核对量（deprecated_since）只是规则读取量的一部分，规则真正该消费的是
            「deprecated 且无代码引用」，而后者我没查；
        (2) 程序 P6 的 `description` 写的是"删除废弃列并清理索引"，但"动作"栏只写了 DROP COLUMN ——
            第二个动作（清理索引）没被点名，属于捆绑不可逆；
        (3) 程序内不可逆动作数 = 2，按规则必须拆成两个程序。
        改为：先拆程序，再执行 SET UNUSED 的最小替代，并在下一块决策里记录观察结果。

**为什么拦住**：`我核对过的量` 是规则读取量的**子集**（只查了时间，没查引用）；
二阶推出了具名实体与连锁成本；反事实提供了更便宜的替代路径；
新增三栏同时命中两条 P5 规则（description 未点名全部动作、程序内不可逆动作数 > 1）。
**指出风险后动作必须改变** —— 这里从 `act` 改成了 `don't-act` + 最小替代 + 拆程序。

## 常见错误

| 错误 | 症状 | 修法 |
| --- | --- | --- |
| 假核对 | `该规则读取的量` 与 `我核对过的量` 不同 | 重查，直到两者一致或明确记录差异理由 |
| 空泛实体 | `受影响实体: 系统` | 具名：服务名、表名、主机名、账户 id |
| 二阶当三阶 | 二阶写"最终结果" | 二阶必须是**直接**后果；三阶才是反应 |
| 有风险无动作变化 | 二阶写了成本，决定仍 `act` 无缓解 | 改成 `act-with-mitigation` 或 `don't-act` |
| 事后补写 | 时间戳晚于动作时间 | 门的意义在于事前；事后补写不算通过 |
| 无决定 | `决定: 再看看 / 待定` | 只允许三个值之一 |
| 一个程序两个不可逆动作（P5） | `程序内不可逆动作数` ≥ 2 | 拆成多个程序，每程序 ≤ 1 个不可逆动作；拆不开就说明这两步本不该在同一意图里 |
| description 写含糊（P5） | `description: 整理一下数据` / 与"动作"栏对不上 | 原样重写为主动语态 5–10 词，且必须点名"动作"栏里的实体与动作 |
| 程序内不可逆动作数 与 动作 栏不符（P5） | 动作栏写了 2 个动作，该栏填 1 | 以程序实际代码为准重数：每一个无法撤销的写入/删除/推送都算一个 |

## 附：本文件与程序账本的联动

- 本文件的每个块对应 `state/programs.md` 里一条程序记录，通过 `程序 id` 关联。
- `ptc_lint.py --kind program` 的硬规则 5：程序账本里 `不可逆动作` 不为「无」时，
  同文件内必须存在至少一个 `## 决策` 块。所以本文件不能只写在本模板副本里，
  必须与程序账本一起交付、一起校验。
- 若同一程序的不可逆动作在推演后被拆开，两个新程序各自需要一块决策，不能只留原来的那一块。
